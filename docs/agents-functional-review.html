FUNCTIONAL WALKTHROUGH · FOR EXPERT REVIEW · DESIGN STAGE

Migration Agents Functional Walkthrough

How each agent in a planned migration platform would do its part of a database migration, shown on one worked example, written for someone who runs migrations for a living.

What this is. A design, not a product. Nothing here is built. Every table, number and log line below is an illustration made up for this document to show intended behaviour.

What we would like from you. Tell us where this does not match how migrations really go. Each agent ends with specific questions, and they are collected again at the end. Blunt answers are the most useful ones.

The idea in one line. Software agents prepare and check the migration paperwork (inventory, profile, plan, mapping, conversion, reconciliation). Ordinary migration tools move the data. People approve every step that cannot be undone.

03

Agent by agent

1

Discovery

Does the inventory you would otherwise build from catalogue queries and a spreadsheet.

How it works

  1. Connects with a read-only user and reads the system catalogue only, no table data.
  2. Lists every table, column, key, index, view, procedure, function and trigger.
  3. Records row counts and storage size.
  4. Builds a dependency graph from foreign keys and from object names referenced inside views and procedures.
  5. Writes a one-line guess at what each table is for, labelled as a guess.
  6. Flags candidates for exclusion: empty tables, tables with backup-style names and no relationships.

You decide

  • What is in scope and what is left behind
  • Dependencies outside the database that it cannot see

It does not

  • Read application code, reports or integrations
  • Detect relationships that exist only by convention, with no declared key

  • Is an undeclared relationship (same column name, no foreign key) common enough that the agent should infer it from data?
2

Profiling

Measures what is actually in the columns before anyone designs around assumptions.

How it works

  1. For each column runs bounded queries: null rate, distinct count, min and max, length spread, common patterns.
  2. Checks declared and suspected relationships for orphan rows.
  3. Checks for values the target engine will refuse: zero dates, invalid encodings, numbers that overflow.
  4. Classifies personal and sensitive columns, by pattern rules first and by name and shape second.
  5. Lists every distinct value of low-cardinality columns for the value mapper.
  6. Ranks findings by how likely they are to break the load.

You decide

  • Fix at source, fix in transform, or reject the rows
  • Whether a sensitivity flag is right

It does not

  • Change source data
  • Guarantee rare bad rows are found in very large tables when sampling is used

3

Strategy

approval: plan

Drafts the migration approach document for an architect to accept or change.

How it works

  1. Collects the facts: total size, largest tables, dependency order, blocking findings, allowed downtime, what the chosen tool can do.
  2. Picks an approach: one-shot load, phased by domain, or load plus continuous sync.
  3. Orders tables into waves from the dependency graph.
  4. Estimates duration and writes down the assumptions behind it.
  5. Lists risks and a rollback approach.
  6. A rule check rejects any plan that breaks dependency order, needs something the tool cannot do, or exceeds the downtime on its own estimate.

You decide

  • Whether the approach is right
  • Everything it cannot know: business calendar, team, contracts, politics

It does not

  • Know real throughput until a rehearsal has run
  • Make the decision; it proposes

Example output

Questions for you

  • What inputs do you need for a credible plan that are missing here?
  • How do you estimate duration before the first rehearsal, and how wrong is it usually?
  • Is the rollback statement honest enough, or is anything short of reverse sync not a rollback in your view?
4a

Schema mapping

Drafts and tests the source-to-target mapping workbook.

How it works

  1. Fixed rules handle the obvious: same names, standard type conversions.
  2. For the rest it shortlists candidate source columns using names, comments and profile statistics.
  3. It picks the best candidate, writes the transform and gives a reason.
  4. Each transform is run on sample rows and checked for truncation, null violations, lost uniqueness and failed casts.
  5. Failed transforms are corrected and re-tested, up to three times.
  6. The draft goes to review with the least certain and untested rows first.
  7. Once approved, the mapping is frozen as a version. DDL, load jobs and validation checks are generated from that version only.

You decide

  • Every mapping it is unsure of
  • Rules for the blocking data findings
  • What is intentionally dropped

It does not

  • Know business meaning beyond names, comments and data shape
  • Allow a change after freeze without a new version

4b

Value mapping

approval: mapping

Prepares the code crosswalks for a business owner to confirm.

How it works

  1. Takes every distinct value and its frequency from profiling.
  2. Matches identical values automatically.
  3. Proposes a target value for the rest, with a reason.
  4. Lists values with no match and values that occur only a handful of times.
  5. Applies nothing until a person confirms each line.

You decide

  • Every mapping. Nothing here is approved automatically.
  • What happens to rows with unmatched values

It does not

  • Know what a code means; it infers from names, labels and usage

5

Code conversion

Produces a first conversion of views, procedures and triggers and says how far each one was checked.

How it works

  1. Orders objects so that dependencies are converted first.
  2. Applies rule-based dialect translation.
  3. Rewrites what rules cannot handle, using the frozen mapping for renamed tables and columns.
  4. Compiles each object in a scratch schema on the target and corrects errors, up to three times.
  5. Runs existing tests or recorded inputs and outputs where they exist.
  6. Labels each object: tested, compiled only, or manual.

You decide

  • Whether "compiled only" objects behave the same
  • Whether logic should move out of the database instead

It does not

  • Deploy to the real target schema
  • Claim equivalence it has not tested

Example output

  • How do you prove a converted procedure behaves the same when there are no tests?
  • Which dialect differences cause silent wrong results rather than errors? Those are the ones we most need to detect.
6

Pipeline build

approval: execution

Turns the frozen mapping and plan into load jobs for whichever tool is in use.

How it works

  1. Asks the tool adapter what the tool supports.
  2. Generates job configuration from the frozen mapping. The same mapping always gives the same configuration.
  3. Sets load order, batch size and parallelism.
  4. Adds pre-load and post-load steps: constraints and indexes off and on, sequence reset, statistics refresh.
  5. Makes each table restartable on its own.
  6. Does a dry run with no data to catch configuration errors.

You decide

  • Tuning for very large tables
  • Whether to start

It does not

  • Silently drop a transform the tool cannot express; it moves it to a post-load step or stops

Example output

Pre-load    create tables without secondary indexes and foreign keys
Wave 1      products, customers            parallel 2, then build id crosswalk
Wave 2      orders                         4 chunks by ord_id range
Wave 3      order_items                    8 chunks by ord_id range
Post-load   apply value maps check, create indexes, add foreign keys,
            reset sequences to max(id)+1, ANALYZE, deploy converted views
Restart     per table and per chunk; a rerun replaces the chunk, never appends

Questions for you

  • Which post-load steps get forgotten most often in real projects?
  • Is chunk-level restart enough, or do you need something finer?
7

Execution

Runs the jobs, watches them, and explains failures instead of leaving someone to read logs at night.

How it works

  1. Applies the approved DDL, then submits jobs wave by wave.
  2. Reports rows, throughput and time remaining per table.
  3. Retries errors on a fixed list of transient causes: dropped connection, lock timeout.
  4. For any other error it reads the message and context and writes a probable cause and a suggested fix.
  5. Stops and calls a person for anything it did not retry.

You decide

  • What to do about any non-transient failure

It does not

  • Edit data or configuration to make a job pass
  • Skip rows on its own

Example output

8

Validation

approval: cutover

Reconciles target against source and produces the evidence for sign-off.

How it works

  1. Generates checks from the frozen mapping, not from free judgement.
  2. Compares row counts, adjusted for rows excluded by an approved rule.
  3. Compares column totals and counts on both sides, applying the transform to the source side.
  4. Compares hashes by key range and narrows down to the differing rows.
  5. Checks references, uniqueness and value-map coverage on the target.
  6. Classifies each difference: load defect, mapping defect, source data defect, or expected by rule.
  7. Pass or fail is decided by the numbers. The written explanation is added afterwards.

You decide

  • Whether each expected difference is truly acceptable
  • Cutover

It does not

  • Waive a failed check
  • Detect a mapping that is wrong but was approved: it validates against the mapping, not against the truth

0

Coordinator

Not a migration role. It keeps the steps in order and the record straight.

How it works

  • Starts each step only when the previous one has produced its output
  • Stops at the four approvals and records who decided, when, and on which mapping version
  • Saves progress continuously, so a crash resumes instead of restarting
  • Sends rework to the step that caused the defect
  • Keeps a log of every statement run against source and target

It does not

  • Make any migration decision
  • Let a step be skipped, even by an administrator
04

What we already know is weak

  • A wrong mapping that gets approved passes validation. Validation proves the data follows the mapping. Review is the only defence, and reviewers get tired.
  • Everything outside the database is invisible. Application code, reports, interfaces and batch jobs that depend on the old schema are not discovered.
  • Converted code that compiles may still behave differently. Without tests there is no proof.
  • The plan is only as good as the estimate. Real throughput is unknown until a rehearsal.
  • The first version is one-shot load only. No continuous sync and no way back after go-live writes begin.
  • For a simple same-engine copy this is overkill. The value is in redesigned targets, engine changes and large object counts.
