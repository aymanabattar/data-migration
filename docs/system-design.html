Migration Platform System Design

Requirements, architecture, component and agent specifications, data model, API, tech stack, security, testing and roadmap for a web platform where agents plan, map and verify data migrations and deterministic engines move the data.

Every number in this document is a design target, not a measurement. Library APIs named here (LangGraph, LangChain, Langfuse) must be checked against current documentation when coding starts.

01

Scope and assumptions

GoalReduce the manual effort and defect rate of database migrations by having agents produce and verify the planning artifacts, with people approving every irreversible step.
In scope, v1Relational source and target. MySQL to PostgreSQL first. User supplies the target schema or accepts a like-for-like one. One-shot load with downtime. Web UI, approvals, validation report.
LaterMore databases, Airbyte and Debezium engines, zero-downtime sync, stored code conversion at scale, multi-tenant hosting.
Out of scopeFile and object storage migration, application code changes, data cleansing of source systems, NoSQL sources.
AssumptionsWorkers can reach source and target over the network. A read-only source user and a target user with DDL rights are provided. One organisation per deployment until Phase 5.
Design rulesAgents plan, engines move. The mapping spec is the single source of truth. Agents see interfaces, never a specific database or tool. Anything executable is verified by execution. People approve what cannot be undone. Every step is resumable.

Non-functional requirements

IDAreaTarget
NFR-01DurabilityA worker crash loses at most the step in flight; the run resumes from the last checkpoint.
NFR-02IdempotencyEvery node and every engine job can run twice without duplicating or corrupting data.
NFR-03Scale, v1One source up to 2,000 tables and 1 TB. Five concurrent migrations per deployment.
NFR-04Source safetyRead-only. Profiling statements capped at 30 s and 10,000 sampled rows; at most 4 concurrent source sessions by default.

NFR-06Data privacyNo unmasked value from a column flagged sensitive is sent to a model or written to a trace.

07

Run lifecycle and failure handling

  1. Operator starts a run. The API creates a migrations row with a thread id and enqueues a job.
  2. A worker takes a lease on the run and invokes the supervisor graph with that thread id.
  3. Each agent subgraph runs. After every node the state is checkpointed and an event is published.
  4. At a gate the graph interrupts. The worker releases the lease; the run shows as waiting for approval.
  5. An approver decides in the UI. The API records the approval and enqueues a resume job with the decision.
  6. After Validation passes and the cutover gate is approved, the report is produced and the run completes.
Run statusMeaningLeaves by
draftConfigured, not startedStart
runningA worker holds the leaseGate, failure, completion, pause
waiting_approvalParked at a gateApprove or reject
pausedStopped by a person or by budgetResume or cancel
failedA node failed past its retry limitRetry from checkpoint or cancel
completed / cancelledTerminal—
FailureHandling
Worker diesLease expires; another worker resumes from the last checkpoint. Nodes are idempotent, so the step in flight is repeated safely.
Model call fails or times outRetry with backoff, three times, then fail the node. Invalid structured output is retried once with the validation error included.
Model output fails verificationRepair loop, up to three attempts, then the item is marked unverified and sent to review.
Source or target unreachableRetry with backoff for a bounded time, then pause the run.
Engine job failsTransient errors retried by the Execution monitor; others diagnosed and escalated. Loads restart per table, not from the beginning.
Validation failsLoad defect returns to Execution; mapping defect returns to Schema mapping with the failing records; source data defect goes to a person.
Budget exceededRun pauses; a person raises the budget or cancels.
Spec edited after freezeNot allowed. A new version is created and downstream artifacts are regenerated.

Abstraction contracts

# Connector: one implementation per database
class Connector(Protocol):
    def capabilities(self) -> Capabilities        # cdc, snapshot, parallel read, max identifier length
    def dialect(self) -> str
    def test(self) -> ConnectionCheck
    def introspect(self, scope: Scope) -> SchemaIR
    def profile(self, table: str, spec: ProfileSpec) -> TableProfile
    def sample(self, table: str, n: int, mask: MaskPolicy) -> Rows
    def query(self, sql: str, mode: Literal["read", "ddl"], approval_id: str | None) -> Result

# Execution engine: one implementation per tool
class ExecutionEngine(Protocol):
    def capabilities(self) -> EngineCapabilities  # full load, cdc, transforms, parallelism
    def plan(self, spec: MappingSpec, order: LoadOrder) -> JobConfig
    def submit(self, job: JobConfig) -> str
    def status(self, job_id: str) -> JobStatus    # per-table rows, bytes, errors
    def cancel(self, job_id: str) -> None

# Schema IR: what agents reason over
SchemaIR   = { schemas: [Schema] }
Table      = { name, columns: [Column], primary_key, foreign_keys, indexes, row_count, bytes }
Column     = { name, logical_type, nullable, default, source_type, comment }
LogicalType= integer(bits) | decimal(p, s) | float(bits) | string(n) | text | boolean
           | date | time | timestamp(tz) | binary | json | uuid | enum(values) | unknown(raw)
Routine    = { kind: view | procedure | function | trigger, name, body, depends_on }
SQL guard ruleApplies to
Statement must parse with sqlglot in the connection's dialectEvery statement
Single statement only; SELECT only; timeout and row limit injectedSource
DDL requires an approval id bound to a frozen spec versionTarget
DROP, TRUNCATE, unbounded DELETE or UPDATE, grants and user management are refusedAgents, always
Statement, agent, trace id and result summary written to the audit logEvery statement

Agent specifications

Model tiers: strong for reasoning and code, fast for classification and summaries. The actual model per agent is configuration. Every agent writes its artifact to the object store and returns only a reference in graph state.

Supervisor

PurposeRun phases in order, enforce gates, route rework, keep the run durable.
InputsMigration id, connection refs, settings, approval decisions.
OutputsUpdated MigrationState; events; audit entries.
GraphOne node per agent subgraph, four gate nodes, conditional edges after gates and after Validation.
ModelNone. Routing is code.
GuardrailsA gate cannot be passed without an approval row from a user with the Approver role. Budget check before each agent.
FailureMarks the run failed with the failing node; retry resumes from the checkpoint.
Done whenReport artifact exists and status is completed.

Discovery

PurposeProduce a complete, neutral inventory of the source.
InputsSource connection ref, scope (schemas to include or exclude).
Outputsinventory: Schema IR, sizes, dependency graph, per-table purpose note, unused-object flags.
Graphlist_schemas → introspect (fan-out per schema) → build_dependency_graph → describe_tables → write_inventory
Toolsintrospect, capabilities, catalogue size queries.
Modelfast for table purpose notes from names, columns and comments. Everything else is code.
GuardrailsReads catalogue only; no table data. Purpose notes are labelled as inferred.
FailureA schema that cannot be read is recorded as skipped with the error; the run continues and the gap is shown.
Done whenObject counts in the inventory equal catalogue counts.
EvaluationInventory completeness against a known sample schema: must be 100%.
2

Profiling

PurposeMeasure data condition and find sensitive columns before design.
InputsInventory, profiling settings (sample size, limits).
Outputsprofile: per-column statistics, issue list with severity, sensitivity class per column, distinct values of low-cardinality columns.
Graphplan_profiles → profile_table (fan-out per table, bounded concurrency) → classify_columns → detect_issues → write_profile
Toolsprofile, masked sample.
Modelfast for sensitivity classification from names, patterns and masked shapes; for plain-language issue explanations.
GuardrailsPattern rules run first and their result cannot be downgraded by the model. Limits from NFR-04. Only statistics and masked shapes reach the model.
FailureA table that exceeds the time limit is profiled on a smaller sample, then marked partial.
Done whenEvery in-scope column has statistics or a recorded reason for none.
EvaluationRecall of sensitive columns on a labelled dataset; recall matters more than precision here.

Strategy

gate: plan
PurposePropose approach, wave order, estimates, risks and rollback.
InputsInventory, profile, downtime budget, engine capabilities, constraints entered by the operator.
Outputsplan: approach, waves with tables, duration estimate with assumptions, risk register, rollback approach, cutover outline.
Graphcompute_facts → order_waves → propose_plan → check_plan → write_plan → gate
ToolsNone against databases. Reads artifacts only.
Modelstrong for the approach decision and risk register. Wave order comes from the dependency graph in code.
Guardrailscheck_plan rejects a plan that uses an ability the engine lacks, breaks dependency order, or exceeds the downtime budget on its own estimate.
FailureIf no plan passes checks after three attempts, the facts and failed checks are shown for a person to plan by hand.
Done whenAn approver accepts the plan.
EvaluationRubric scoring by reviewers; later, estimate against actual duration.
4a

Schema mapper

PurposeProduce the verified mapping spec.
InputsSource IR, target IR (supplied or like-for-like), profile.
Outputsmapping_records rows: target column, source columns, kind, transform, types, null handling, confidence, verified flag, rationale, status. Key plan and ID crosswalk design. Target DDL after freeze.
Graphrule_pass → generate_candidates → rank (fan-out per table) → verify → repair loop → assemble → review → freeze → generate_ddl
ToolsVector search over column embeddings, sample (masked), query on a scratch schema for transform tests.
ModelEmbeddings for candidates. strong for ranking and transforms, with structured output.
GuardrailsTransforms must parse and run on samples; checks for truncation, null violations, uniqueness loss, cast failures. Model confidence is capped when verification is missing. Unmapped required target columns block the freeze.
FailureItems that fail repair are kept as unverified and sorted to the top of review.
Done whenEvery target column has an approved record or an approved reason to be empty.
EvaluationMatch precision and recall; transform correctness by execution; count of wrong mappings above 0.8 confidence; share edited by reviewers.
4b

Value mapper

gate: mapping
PurposeMap codes and categories whose meaning differs between systems.
InputsMapping records of kind lookup, distinct values and frequencies from the profile, target allowed values.
Outputsvalue_maps: source value, target value, frequency, reason, status.
Graphselect_code_columns → exact_match → propose_matches → flag_unmatched → review → attach_to_spec
Modelfast for proposals.
GuardrailsNothing is auto-approved. Values with no match must get an explicit decision: map, default, or reject rows.
FailureToo many distinct values (over a set limit) means the column is not a code column; it is returned to the Schema mapper.
Done whenEvery source value seen in the data has an approved outcome.
EvaluationAccuracy against labelled crosswalks.

Code conversion

PurposeTranslate views, procedures, functions and triggers to the target dialect.
InputsRoutines from the inventory, frozen spec (for renamed objects), target dialect.
Outputsconverted_code: per object the new body, status (tested, compiled, manual), notes on behaviour differences.
Graphorder_by_dependency → transpile_rules → convert_llm → compile_on_scratch → repair loop → run_tests_if_any → classify → write
Toolssqlglot transpile, query in DDL mode on a scratch schema only.
Modelstrong for what rules cannot translate.
GuardrailsNever deployed to the real target schema by this agent. "Compiled" is never reported as "tested".
FailureAfter three failed repairs the object is marked manual with the last error.
Done whenEvery routine has a status.
EvaluationCompile rate; behavioural match on routines that have recorded inputs and outputs.

Pipeline builder

gate: execute
PurposeTurn the frozen spec and plan into engine job configuration.
InputsFrozen spec version, plan, engine capabilities.
Outputsjob_config per wave, load order, pre-load and post-load steps (constraints, indexes, sequences).
Graphcheck_capabilities → build_load_order → engine.plan → dry_run_validate → write → gate
ModelNone by default.
GuardrailsOutput is deterministic from the spec (NFR-11). A transform the engine cannot express is moved to a post-load SQL step or reported, never dropped.
FailureCapability gaps stop the run with a list of what the chosen engine cannot do.
Done whenDry-run validation passes and an approver allows execution.
EvaluationSnapshot tests: same spec, same config.

Execution monitor

PurposeRun jobs, report progress, handle and explain failures.
InputsJob configs, approval id.
Outputsjobs rows with per-table rows, bytes, duration, errors; diagnosis notes.
Graphapply_ddl → submit → poll loop → on_error: classify → retry | diagnose → escalate → post_load_steps
Toolssubmit, status, cancel; target query in DDL mode with the approval id.
Modelfast to turn an engine error and context into a probable cause and suggested fix.
GuardrailsRetries only errors on a transient list. Never edits data or config to make a job pass.
FailureUnclassified errors pause the run with the diagnosis attached.
Done whenAll tables in the wave report loaded and post-load steps succeed.
EvaluationDiagnosis accuracy on a library of injected failures.

Validation

gate: cutover
PurposeProve the target matches the source under the spec, or locate every difference.
InputsFrozen spec, both connection refs, job results.
Outputsreconciliation: per-table and per-column check results, mismatch samples (keys only), defect class per mismatch, summary for sign-off.
Graphgenerate_checks → run_checks (fan-out per table) → drill_down_mismatches → classify_defects → explain → write_report → route
ChecksRow counts; column aggregates; hash comparison by key range with bisection to find differing rows; reference integrity; transform spot checks; value-map coverage.
Modelfast for explanations. Pass or fail is decided by code only.
GuardrailsChecks are generated from the spec, not written by the model. A failed check can never be waived by an agent.
FailureChecks that cannot run are reported as not verified, which blocks the cutover gate unless an approver accepts them by name.
Done whenAll checks pass or each exception is accepted by an approver.
EvaluationDetection rate on targets with injected defects: missing rows, altered values, wrong mapping.

Observability and evaluation

  • One Langfuse trace per agent invocation, tagged with migration id, agent, spec version and model.
  • Prompts live in the Langfuse registry and are loaded by name and label; the prompt version is recorded on each trace.
  • Cost is summed per migration and compared with the budget before each agent starts.
  • Golden datasets: at least three schema pairs with hand-written mappings, a labelled sensitive-column set, labelled crosswalks, a failure library, and targets with injected defects.
  • CI runs the evaluations on every prompt or model change and blocks the merge when a score falls.
  • Reviewer edits in production are written back as scores, so real corrections become new evaluation cases.
  • System health (queue depth, worker leases, API latency, engine throughput) goes to Prometheus, not Langfuse.
