Migration Agents Reference

What each of the ten agents does, which step of an industry migration project it supports, and what difference it should make.

Nothing here has been built or measured yet. Impact statements are expectations, each marked Likely for a strong inference from how migrations are done today, or Guessing where there is no evidence yet. No percentages are quoted because none have been measured.

The agents

0

Supervisor

Runs the migration as a fixed sequence of phases and stops at every approval gate.

LLM use: noneInput: events and approvalsOutput: run state, audit trail

What it does

  • Starts each agent in order and passes it references to earlier outputs
  • Saves progress after every step so a crashed run resumes where it stopped
  • Pauses at four gates (plan, mapping, execute, cutover) until a person decides
  • Sends work back to the right phase when validation finds a defect

Industry process

Migration programme governance: stage gates, go/no-go decisions and the cutover runbook. Today this lives in project plans, meeting minutes and a runbook spreadsheet kept by a migration lead.

Most useful when

  • Runs last hours or days and must survive restarts
  • Regulated work needs proof of who approved what
  • Several migrations run at once

Expected impact

  • LikelyNo step can be skipped or run out of order
  • LikelyApproval evidence is produced as a by-product, not assembled afterwards
  • GuessingOne lead can oversee more parallel migrations

Limit: it enforces the process; it does not judge whether an approval was wise. A careless approver still passes the gate.

1

Discovery

Finds out what exists in the source: objects, sizes and what depends on what.

LLM use: lowInput: connection referenceOutput: inventory, dependency graph

What it does

  • Reads the catalogue: schemas, tables, columns, keys, indexes, views, procedures, triggers
  • Records row counts and storage size per table
  • Builds a dependency graph from foreign keys and code references
  • Describes each table's likely purpose and flags unused or empty objects
  • Stores everything in the neutral schema model the other agents read

Industry process

The assessment phase of every cloud and database migration method. Normally done by a data architect with catalogue queries, vendor assessment reports and interviews, then written into an inventory spreadsheet.

Most useful when

  • Legacy systems have little or outdated documentation
  • Mergers bring in systems nobody on the team knows
  • Many databases must be sized to plan a programme

Expected impact

  • LikelyInventory in hours instead of days for a single database
  • LikelyUnused objects identified early, shrinking scope
  • LikelyCorrect load order derived from dependencies, not memory

Limit: it sees only what the database knows. Dependencies in application code, reports and external integrations still need people to name them.

2

Profiling

Measures the actual condition of the data before anyone designs around it.

LLM use: mediumInput: inventoryOutput: data quality report, PII flags

What it does

  • Runs bounded, sampled queries per column: null rate, distinct count, ranges, lengths, patterns
  • Detects duplicates, orphan records and broken references
  • Spots encoding, date and precision problems that break on a new engine
  • Classifies columns that hold personal or sensitive data
  • Lists distinct values of code columns for the value mapper

Industry process

Data quality assessment and data classification. Usually a data analyst writing profiling queries or using a data quality tool, with privacy classification done separately for compliance.

Most useful when

  • Old systems have years of loosely validated input
  • Target has stricter constraints than source
  • Privacy rules apply: GDPR, India's DPDP Act, HIPAA, PCI-DSS

Expected impact

  • LikelyData defects surface before build, when they are cheap to fix, not at cutover
  • LikelySensitive columns are masked for the rest of the run automatically
  • GuessingFewer failed mock runs

Limit: sampling can miss rare bad rows in very large tables, and it reports problems without fixing them. Cleansing decisions remain with the data owner.

3

Strategy

Proposes how to migrate: approach, order, downtime and the way back.

LLM use: highInput: inventory, profile, downtime budgetOutput: migration planGate: plan

What it does

  • Chooses between one-shot, phased and continuous-sync approaches from size, allowed downtime and engine abilities
  • Groups tables into waves that respect dependencies
  • Estimates duration and states the assumptions behind the estimate
  • Lists risks and a rollback approach for each wave
  • Drafts the cutover runbook outline

Industry process

Migration planning and design: approach selection, wave planning, cutover and rollback planning, recovery targets. Normally a solution architect's document reviewed by a design board.

Most useful when

  • The team has little migration experience
  • Many similar databases need consistent plans
  • Downtime limits are tight and options must be compared

Expected impact

  • LikelyA first plan draft in minutes, with reasoning written down
  • LikelyA rollback approach exists for every run, which manual plans often omit
  • GuessingEstimates become more accurate as past runs are fed back

Limit: this is the agent whose output is least checkable by machine. It does not know business calendars, contracts or team capacity. Treat the plan as a draft for an architect, never as a decision.

4a

Schema mapper

Works out where every source column goes in the target and how it must change.

LLM use: highInput: source and target schema, profileOutput: mapping spec, target DDL

What it does

  • Matches tables and columns, including splits, merges and derived fields
  • Converts data types and flags truncation or precision loss
  • Writes the transform expression for each column
  • Plans new keys and the old-to-new ID crosswalk
  • Runs every transform on sample data before a person sees it
  • Presents the least certain mappings first for review

Industry process

Source-to-target mapping, the central document of any migration, plus schema conversion. Today analysts fill a mapping workbook by hand; vendor schema converters handle types but not meaning.

Most useful when

  • Moving between applications with different data models, such as ERP or CRM replacement
  • Warehouse modernisation with hundreds of tables
  • Consolidating systems after a merger

Expected impact

  • LikelyAnalysts review and correct a draft instead of writing every row; this is usually the largest block of manual effort
  • LikelyTransform errors are caught by execution before build
  • LikelyDDL, pipeline and checks come from one spec, so they cannot drift apart

Limit: for a same-schema move between two engines, most of this is a lookup table and the model adds little. The risk to watch is a wrong match returned with high confidence; review and evaluation exist for that.

4b

Value mapper

Translates codes and categories whose meaning differs between systems.

LLM use: mediumInput: distinct values from profilingOutput: value mapping tablesGate: mapping

What it does

  • Collects the distinct values of status, type, country, currency and similar columns
  • Proposes the matching target value for each, with a reason
  • Flags values with no match and values that appear only a few times
  • Always asks a business owner to confirm

Industry process

Reference data and master data harmonisation: building crosswalk tables. Normally workshops between analysts and business users, and the step most often left until late.

Most useful when

  • ERP and finance moves with charts of accounts and cost centres
  • Healthcare and insurance with coded diagnoses and products
  • Merging two companies' customer or product categories

Expected impact

  • LikelyCatches errors that row counts and checksums cannot: data arrives intact but means the wrong thing
  • LikelyBusiness users confirm a prepared list instead of starting from a blank sheet

Limit: meaning is business knowledge. The agent cannot verify its suggestions by running anything, so nothing here is applied without sign-off.

5

Code conversion

Rewrites database logic for the target engine.

LLM use: highInput: views, procedures, triggers, functionsOutput: converted code, confidence flags

What it does

  • Translates views, stored procedures, functions and triggers into the target dialect
  • Uses rule-based translation first and a model for what rules cannot handle
  • Compiles the result on the target and retries on errors
  • Marks each object as tested, compiled only, or needs manual work

Industry process

Database code conversion in engine changes, such as Oracle to PostgreSQL or Teradata to a cloud warehouse. Done by database developers with vendor converters, followed by long manual clean-up.

Most useful when

  • Leaving a commercial database to cut licence cost
  • Warehouse moves with thousands of SQL scripts
  • Systems where much business logic lives in procedures

Expected impact

  • LikelyDevelopers start from compiling code instead of rewriting from scratch
  • LikelyThe hard objects are identified up front, improving estimates
  • GuessingShortens what is often the longest part of an engine change

Limit: code that compiles is not code that behaves the same. Without existing tests or recorded inputs and outputs, equivalence cannot be proven, and complex procedures still need a developer.

6

Pipeline builder

Turns the approved mapping and plan into a runnable job for the chosen tool.

LLM use: very lowInput: frozen spec, plan, engine abilitiesOutput: job configuration, load orderGate: execute

What it does

  • Asks the engine adapter what the tool supports
  • Generates job configuration from the frozen spec
  • Orders loads by dependency and sets batch sizes and parallelism
  • Makes every job restartable and safe to run twice

Industry process

The build phase: writing migration scripts or configuring an ETL or replication tool. Done by data engineers, and tied to whichever tool the organisation bought.

Most useful when

  • Different clients or teams use different migration tools
  • The same migration must be rehearsed many times
  • A tool must be swapped mid-project

Expected impact

  • LikelyThis is what makes the platform tool-agnostic: one spec, many engines
  • LikelyNo hand-written job can disagree with the approved mapping

Limit: mostly templates, not intelligence. Each new tool still costs an adapter, and tuning for very large tables needs an engineer.

7

Execution monitor

Runs the jobs, watches them and explains failures.

LLM use: lowInput: job configurationOutput: run status, failure diagnosis

What it does

  • Submits jobs through the engine adapter and tracks progress and throughput
  • Retries transient failures within set limits
  • Reads engine errors and proposes the likely cause and fix
  • Stops and escalates on anything it cannot classify

Industry process

Mock runs, the production load and cutover-night operations. Today engineers watch logs, often overnight, and restart failed steps by hand.

Most useful when

  • Loads run for many hours
  • Several rehearsals are needed before the real run
  • Continuous sync must be watched until cutover

Expected impact

  • LikelyLess time between a failure and knowing why
  • LikelyEngineers are called for real problems, not for transient retries
  • GuessingRehearsals get cheap enough that teams run more of them

Limit: it never changes data to make a job pass. A diagnosis is a suggestion; anything beyond a retry needs a person.

8

Validation

Proves the target holds what the source held, or says exactly where it does not.

LLM use: mediumInput: frozen spec, source, targetOutput: reconciliation reportGate: cutover

What it does

  • Generates checks from the spec: row counts, column totals, hash comparison by key range, reference integrity
  • Re-applies transforms to source samples and compares with the target
  • Classifies each mismatch as a load defect, a mapping defect or a source data defect
  • Explains mismatches in plain language and routes rework to the right phase
  • Produces a report fit for sign-off

Industry process

Reconciliation and acceptance. Usually testers compare counts and a sample of records, then assemble evidence for business and audit sign-off.

Most useful when

  • Banking, insurance and finance, where totals must reconcile exactly
  • Audited environments such as SOX-controlled systems
  • Any migration too large to check by sampling

Expected impact

  • LikelyEvery table and column is checked, not a sample
  • LikelySign-off evidence is generated, not compiled by hand
  • LikelyDefects go back to their cause, avoiding pointless reloads

Limit: it proves the data matches the spec. If the spec itself is wrong, validation passes. That is why mapping review and value sign-off cannot be skipped.
